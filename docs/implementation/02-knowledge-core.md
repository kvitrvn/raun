# Epic 2: knowledge core

Epic: #8. Review: #9. Decided by the owner on 2026-11-11.

## Scope

Rebuild the core of Raun, independent of any server: the knowledge model, deterministic evidence verification and a database store with revision-checked updates. Later epics add triggers, runners and screens without revisiting what a knowledge item is.

Sources consulted: `kvitrvn/raun-old` at `330e634` (`docs/format.md`, `docs/agents.md`, `AGENTS.md`, `internal/evidence`, `internal/knowledge`), and issues #8 and #10 to #15.

The normative tables (fields, statuses, transitions, evidence states, identifiers, revisions, format versions) are in [docs/format.md](../format.md). This page records why.

## Choices

### Item model

The model of raun-old is kept as it is: the types `persona` and `requirement`, the requirement kinds `business-rule`, `functional` and `constraint`, the five statuses and their transitions, support with its two natures, evidence with its sources and states, open points with their kinds, positions and resolutions.

Two adjustments keep `proposed` free of unresolved disagreements, which raun-old implied without enforcing:

- the unreachable `contested` to `validated` row is dropped, since resolving the last disagreement already makes the item `proposed`;
- reopening a `rejected` item that holds an unresolved disagreement makes it `contested`, not `proposed`.

One change of behavior: an excerpt that is not at its cited lines but appears at several other places is reported as `ambiguous` instead of being moved to the nearest occurrence. raun-old's choice could attach a claim to the wrong code without anyone noticing. Ambiguity is a reason, not a fifth state: the integrity check reports it as `invalid`, the freshness check as `stale`, so every rule that reads states stays as it was. A citation found ambiguous at its own commit is therefore never checked again, where raun-old would have relocated it and kept following it: it supports nothing, and the next analysis cites the code anew. The other reasons (`not-found`, `missing-file`, `not-regular`, `binary`, `too-long`, `bad-range`) say why a citation has no ground, which raun-old only wrote in its run manifests.

Three rules were made explicit while implementing the model (#10):

- A requirement's `kind` is optional, as in raun-old, but a value outside the three kinds is refused.
- History events are in time order, and a change dated before the last change of the item is refused: a clock or a replayed run cannot rewrite the order of decisions.
- A position of a disagreement keeps the run that wrote it. A conflict with existing content therefore sets a position of an earlier run of the item against one of the current run, and a run unknown to the item is refused.

Adding a type later takes a constant in the core, a row in `docs/format.md` and a decision in the record of the epic that adds it. The set of types is closed: an unknown type is a validation error.

### No import from raun-old

raun-old was never used in production, so there is no knowledge base to bring over. Raun has no importer and no compatibility with raun-old files, identifiers or run manifests; raun-old is only its functional specification. #15 is closed as not planned, and the epic 1 record no longer mentions an import.

Until LLM analysis exists (epic 10), tests seed knowledge through the storage port.

### Identifiers

An item identifier keeps the raun-old form, `<type>-<6 characters>` from an alphabet without look-alike characters. It is unique within a repository, not across the instance. It is short enough to read in a pull request comment and to type in a search, and 31^6 (about 887 million) values per type and repository make a collision rare. A collision is still handled: the store refuses the identifier and the caller draws another.

The identifier is generated by the core (`NewID` from a type and a random source), not by the store, so that tests can make it deterministic.

### Revisions

A revision is an integer counter: `1` at creation, one more on every successful update. An update states the revision it read and is refused if the stored one differs.

raun-old used a SHA-256 of the canonical content. A counter needs no canonical serialization to compare, costs a single `WHERE revision = ?` on any SQL engine, and survives a change of the stored representation. It also changes on an update that leaves the content the same, which is harmless: that update was still a write. The canonical serialization of an item is now needed only by the exports (epic 11).

### Storage shape

An item is one row: indexed columns for what queries filter or sort on (workspace, repository, identifier, type, status, revision, title, creation and update times) and one JSON document for the rest (the type-specific content, support, evidence, open points).

Its status history is a separate table, one row per event.

- **Why a document.** An item is read and written whole, through `Get` and `Update`, and its sub-elements (support, observations, evidence, positions) refer to each other by identifiers local to the item. Normalized tables would mean six or seven tables, their migrations and their mapping code, for queries no epic needs. The JSON encoding is deterministic: struct fields in a fixed order, slices in a stable order.
- **Why history apart.** It is append-only, and a table of its own lets the database enforce that, and lets later epics list the decisions of a repository without decoding every item.

The document is an internal representation, changed only through a migration. It carries no `version` field; the schema version covers it.

### History

History is append-only.

- The store writes the new events of an update in the same transaction as the item, and refuses an update whose mutation changes or removes an existing event.
- SQLite triggers abort any `UPDATE` or `DELETE` on the history table. Epic 14 does the same on PostgreSQL.
- The item's `status` column always equals the `to` of its last event, written in the same transaction.

An event records `actor` (`human` or `run`) and `by`. For a human, `by` identifies the account that decided. Accounts arrive in epic 4; until then `by` is an opaque identifier given by the caller, never text typed by the person deciding, and epic 4 binds it to an account. For a run, `by` is the run identifier.

### Scoping

Every row carries a workspace identifier and a repository identifier, items and history events alike. The primary key of an item is `(workspace, repository, id)`; history events reference it with the same three columns. Repository identifiers are not assumed unique across workspaces until epic 5 decides whether a repository belongs to one workspace only (#30).

The scope is a value (`Scope{Workspace, Repository}`) passed to every port operation, not a property of a store instance. One store serves the whole server, and an operation without a scope does not exist. Every query filters on both identifiers, so a read cannot cross repositories. The contract tests prove it on each table.

Workspaces and repositories have no table yet (epics 4 and 5). Until then their identifiers are opaque non-empty strings, and the foreign keys to their tables are added by the migrations of those epics.

### SQLite

The first production dependency is the driver `modernc.org/sqlite`: SQLite translated to Go, so the binary keeps building with `CGO_ENABLED=0` as the Makefile requires. It is the most used pure-Go SQLite driver and is reached through `database/sql`. Its costs are a larger binary and a longer first build. #14 adds it to `go.mod` and to the dependency table of `AGENTS.md` together, and runs `make vuln` on it.

| Setting | Value | Why |
| --- | --- | --- |
| Journal mode | WAL | Readers do not block the writer, nor the writer the readers. |
| Writer | One connection dedicated to writes, transactions started with `BEGIN IMMEDIATE` | SQLite allows one writer; one connection makes that explicit instead of retrying lock errors. |
| Readers | A separate pool | Reads run in parallel with the writer. |
| `busy_timeout` | 5 seconds | A checkpoint or a backup does not fail a request at once. |
| `foreign_keys` | On | Off by default in SQLite. |
| `synchronous` | `NORMAL` | Safe with WAL; a power loss may lose the last transaction, not corrupt the database. |

No SQLite syntax leaves the adapter, which keeps a PostgreSQL adapter possible (epic 14, #93).

### Migrations

Migrations are numbered SQL files (`0001_<slug>.sql`, ...) embedded in the binary, applied in order, each in its own transaction, and recorded in a `schema_migrations` table.

They run at server start, and only when the administrator enables it with a setting (`RAUN_DATABASE_MIGRATE=true`; epic 3 defines the variable). Without it:

- a schema older than the binary stops the server, with a message naming the setting;
- a schema newer than the binary always stops the server, enabled or not: an older binary never writes to a database it does not know.

Migrations are never applied on first use of a connection. There are no down migrations; whether downgrades are supported is settled in epic 13. The runner never opens the database. Epic 2 provides the migration function in the SQLite adapter; epic 3 (#18) calls it at start.

### Storage port

The port is declared in the knowledge core:

| Operation | Contract |
| --- | --- |
| `List(ctx, scope, filter)` | Items of the repository matching the filter (type, status), ordered by identifier. |
| `Get(ctx, scope, id)` | The item, or `ErrNotFound`. |
| `Create(ctx, scope, item)` | Stores a new item at revision 1 with its creation event. `ErrIDTaken` if the identifier exists in the repository. |
| `Update(ctx, scope, id, revision, mutate)` | Runs `mutate` on the stored item inside the write transaction, then stores it at revision + 1 with its new events. `ErrNotFound`, `ErrStaleRevision` when the stored revision differs. An error returned by `mutate` rolls everything back and is returned as it is. |

The validation of the item and of its transitions runs in the core before anything is written: the store never writes an item the core would refuse. The one rule the core cannot check alone, that the personas a requirement names exist in the repository, is checked by the store inside the write transaction, and `Create` or `Update` fail with `ErrUnknownReference`. There is no `Delete`: an item is rejected, never deleted on its own.

There is no `Save` (create or replace): replacing an item without a revision check is exactly what the port exists to prevent.

### Commit reader and sources

Rules made explicit while implementing the commit reader and the classification (#11):

- **The reader is bound to one repository.** `knowledge.CommitReader` has three operations, `ResolveRevision`, `ListTree` and `ReadFiles`, and none takes a repository: the adapter is opened on one directory, the top of a working tree or a bare repository, as a runner gets one repository per job (T15). A directory below the root is refused, so Git never looks above it.
- **`ReadFiles` visits instead of returning.** It calls a function once per distinct path, in byte order, so memory holds one file at a time whatever the number of paths. Every requested path is visited, with what the commit holds there: a file with its content, a directory, a link, a submodule, or nothing. A link is never followed and a submodule never entered.
- **No path reaches Git.** A path is checked by `knowledge.ValidatePath`, which refuses a path starting with a dash on top of the rules evidence paths already had, then looked up in the tree listing; Git receives the object name only, on the standard input of one `cat-file --batch`. The same rule applies to the `path` of an evidence, so an evidence citing `-x` is refused. Only the first byte counts: `dir/-x` is a valid path. A revision starting with a dash is refused, and the others are passed after `--end-of-options`.
- **Three processes per read.** Reading the files of one commit checks the commit, lists its tree and reads the blobs: three processes whatever the number of files, two when no file has content to read. The tree is listed whole rather than with pathspecs, so that no path becomes an argument.
- **Git runs in a controlled environment.** The environment is built from nothing; the user and system configuration are ignored; hooks, the file system monitor, the pager, lazy fetching and replacement objects are disabled on the command line, over the configuration of the repository. Every transport is denied by an empty `GIT_ALLOW_PROTOCOL`, which overrides a `protocol.<name>.allow` of the repository where `protocol.allow=never` does not. A partial clone is refused at `Open`: Git before 2.44 ignores `GIT_NO_LAZY_FETCH` and would fetch a missing object from the promisor remote, and Raun needs every file of the commit anyway. `safe.directory` is not relaxed: a repository owned by another user is refused, as Git refuses it. Git 2.32 or later is required, the first with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM`.
- **Bounds.** A file above 8 MiB is reported as too large, with no content; a tree above one million entries is refused with `knowledge.ErrTreeTooLarge`. Both are options of the adapter. `ReadFiles` holds one file at a time, but `ListTree` returns the whole tree sorted, so it holds every entry: about a hundred bytes each, some hundred megabytes at the bound.
- **Binary.** A file is binary when its first 8000 bytes hold a NUL byte, the rule Git uses. `knowledge.IsBinary` states it in the core, so an in-memory reader gives the same answer.
- **Sources keep the model of raun-old.** The context set lists exact paths, the documentation and exclusion sets list patterns, and the precedence is context, then exclusion, then documentation, then code: a context file stays human context inside an excluded directory. The default documentation patterns are raun-old's (`**/*.md`, `**/*.rst`, `**/*.adoc`, `**/*.txt`, `docs/**`); there is no default context or exclusion. `DefaultDocs` returns a new slice, and an empty documentation set means no documentation, so epic 8 decides how a configuration that omits the set maps to the default.
- **Patterns are matched in linear time.** `**` is matched like a wildcard over segments, going back only to the last `**`, so a pattern from the repository configuration cannot make the match explode. A pattern that could match no clean path (empty, absolute, an empty, `.` or `..` segment, a malformed class) is refused, so a typo is not silently inert.

`internal/gittest` lands with #11, whose adapter tests need it; `internal/golden` stays in #12.

Rules made explicit while implementing the golden-file helper (#12):

- **One function.** `golden.Equal(t, path, got)` compares byte for byte, with no normalization of line endings or order: the caller makes its output deterministic. `.gitattributes` marks every `testdata` directory `-text`, so Git never converts line endings on checkout. A failure names the first line that differs, quoted and bounded, and the size of both sides.
- **The flag without a variable.** The package registers `-update` at init unless another package already did, and reads it back through `flag.Lookup` when `Equal` runs, so it holds no package-level state and a consumer needs no `TestMain`. A flag of that name defined elsewhere is accepted only if it is a boolean that defaults to false; otherwise `Equal` fails, since such a flag could rewrite every golden file on a plain run. Files are refreshed one package at a time, `go test ./<pkg> -update`: a test binary that does not import the helper refuses the flag, so `./...` cannot be used.
- **Writes stay in testdata.** A golden path must be clean, local to the package directory, lie in a `testdata` directory, go through no symbolic link and name a regular file, when comparing as when updating, so a file that can be read can always be refreshed and an update never writes through a link. An update writes a temporary file in the same directory and renames it, with mode 0644 whatever the umask, so it never leaves a partial file. Without `-update`, nothing is written.

### Evidence limits

The maximum length of a citation stays 40 lines by default. It is a parameter of the verification, with that default; the repository configuration may change it from epic 8.

### Evidence verification

Decided by the owner on 2026-11-12 (#13): a citation whose file is larger than the reader reads gets a new reason, `too-large`, allowed with `invalid` and `stale` like `missing-file`. Its content was not read, so `binary` or `not-found` would not be true, and failing the whole check would let one citation of a large file block every other. The reason is a value of the item document, which has no `version` field and holds no stored data yet (#14 is not merged), so nothing is migrated.

Rules made explicit while implementing it (#13):

- **A verifier on the port.** `knowledge.Verifier` is built once from a `CommitReader` and the maximum number of lines (0 for the default of 40, a negative value refused). `Integrity` checks evidence at the commits they cite, `Freshness` at a later commit. Both take the time of the check from the caller, return new evidence in the order given and never change the input. They read each commit once, through one `ReadFiles` call with the distinct paths, and decide every citation of a file while it is visited, so one file is held at a time. An error means the check could not run (an invalid input, an unknown commit, a tree above the bound, a canceled context); it never stands for a state.
- **The order of integrity.** A range that starts before line 1 or is reversed is `bad-range` before anything is read; then a citation longer than the maximum is `too-long`; then the file gives `missing-file`, `not-regular`, `too-large` or `binary`; then a range past the last line is `bad-range`. A range that is both reversed and long is `bad-range`, since the model keeps the range of a `bad-range` citation only.
- **What the maximum counts.** Both the cited range and the excerpt without its blank ends; either one above the maximum is `too-long`. Freshness does not apply it: the maximum was checked at integrity and may change with the repository configuration (epic 8).
- **What blank means.** Only spaces and tabs, as `docs/format.md` says; raun-old also collapsed every Unicode space. Blank lines are dropped at both ends of the excerpt and of the cited range, and kept inside them. An excerpt that is blank once normalized is found nowhere: `not-found`.
- **A match at the cited lines wins.** An excerpt at the cited lines is `verified` even if it also appears elsewhere. Otherwise its occurrences are counted, overlapping ones included: one is a relocation, two or more are `ambiguous`. A relocation corrects the lines to the occurrence without its blank ends, and never changes the excerpt or its hash.
- **Freshness gives verified or stale.** A `relocated` evidence that holds at a later commit becomes `verified`, as the table of states says; its corrected lines stay. An `invalid` evidence is returned as it is and its file is not read. An evidence without a state is refused.

### Format versions

The invariant of `AGENTS.md` stands: every format read or written outside the database carries a `version` field, and the database schema is versioned by its migrations. The table is in [docs/format.md](../format.md#format-versions). A format with an unknown version is refused.
